# Toolbox validation tools

Two small validators. Both run as CI gates in
[`.github/workflows/toolbox-ci.yml`](../../.github/workflows/toolbox-ci.yml) and both are
worth running locally before you open a PR:

```bash
python Toolbox/tools/validate_artifact_paths.py
python Toolbox/tools/verify_hashlocks.py
```

`validate_artifact_paths.py` needs PyYAML (`pip install pyyaml`); `verify_hashlocks.py`
needs nothing beyond the standard library.

---

## Why these exist

Both gates exist because of a specific, documented failure, not as generic hygiene.

The Toolbox's first published contract described **seven endpoints that no CBWeb3 gateway
has ever served**. Mocks, test vectors, conformance tests, tutorials and CI were all built
on top of them, and the whole set shipped **green for four sessions**. Spectral validated
the contract's syntax. `ajv` validated the fixtures' shape. Prism served the fiction the
contract described, so the smoke test passed too. Nothing validated the one relationship
that mattered: *does this endpoint exist?*

Separately, every artifact published a SHA-256 digest that was **not the hash of anything**,
and told implementers to verify it. An integrator who followed the instruction got a
mismatch and had no reason to suspect the Toolbox rather than their own code.

Neither failure was subtle. Both were invisible because nothing checked for them.

## `validate_artifact_paths.py`

Answers one question for every fixture:

> Does `<METHOD> <path>` exist on a gateway the Toolbox describes?

It loads every `Toolbox/contracts/*/openapi_*.yaml`, builds the union of published path
templates and their methods, and resolves the `request.path` of each mock and the
`input.path` of each test vector against it.

- Concrete identifiers match templated segments:
  `/api/v1/payments/fx/agreements/aaeca49d-…/accept` resolves against
  `/api/v1/payments/fx/agreements/{tradeId}/accept`.
- Query strings are ignored — they are parameters, not paths.
- A path that resolves but does not declare the method is a failure, reported separately
  from a path that does not exist at all.
- The union of all three contracts is checked, because a fixture may legitimately target
  `auth`, `pvp` or `amm`.

**What it does not check:** that a fixture's request *body* satisfies the operation's
`requestBody` schema. That is a worthwhile next gate; see the contribution table in
[`../docs/onboarding/README.md`](../docs/onboarding/README.md).

## `verify_hashlocks.py`

Recomputes every secret / hash-lock pair the repository publishes.

**The derivation is easy to get wrong, and getting it wrong is the most common way a first
HTLC integration fails.** The gateway carries the secret as **64 lowercase hex characters
(32 bytes)** and hashes the **decoded bytes**:

```
hash_lock = SHA-256(hex_decode(secret))
```

It does *not* hash the ASCII of the string you send, so a human-readable passphrase is not
a valid secret — anything that is not 64 hex characters is rejected with
`400 "hash_lock must be a 64-char hex string (32 bytes)"`.

The tool checks the hex-decoded derivation first and falls back to the ASCII derivation, so
a pair using the older convention is still verified rather than silently skipped — but the
fallback is reported as a warning, because a real gateway would reject that secret.

Pairs are collected from four places:

1. `syntheticSecrets` blocks in `Toolbox/test-vectors/*/*.json`, pairing keys by name
   (`secretHex`/`hashLock`, `wrongSecretHex`/`wrongSecretHash`, …).
2. `Toolbox/mocks/**/*.json`, **grouped by `contract_id` across files** — when one fixture
   reveals a secret and another carries the matching lock's digest, the pair is verified.
   This is the check that matters most: the settle fixture is the one an integrator copies.
3. `HTLC_SECRET` / `HTLC_HASHLOCK` in `Toolbox/sandbox/sample-configs/.env.example`.
4. Markdown reference tables and `printf … | sha256sum` verification one-liners across
   `Toolbox/**/*.md`, including inside blockquote callouts.

Two results are **not** failures and are reported for information:

- A hash lock that reuses a digest already verified above. Both legs of an HTLC swap share
  one hash lock, so this is exactly right.
- A hash lock published with no secret. A live lock's secret is generated by the gateway and
  stays private until settlement, so a fixture for an unsettled or refunded lock legitimately
  publishes only the digest.

The discredited pre-realignment digest is rejected outright wherever it appears as a
published value. A companion CI step greps the working tree and fails on **any** occurrence
of the full 64-character literal, retraction notes included — a grep cannot tell a field
value from a sentence about a field value, so it refuses both. That is why every retraction
in this repository writes the digest elided (`7f83b165…`). If you need to cite it in full,
you cannot: elide it, and let `verify_hashlocks.py` — which parses the artifacts and *can*
tell the difference — enforce the value-level rule.

## Adding a gate

A new gate belongs here when it checks a **relationship between artifacts** that no
single-file validator can see. Schema-shape checks belong in
[`../schemas/`](../schemas/) and are enforced by `ajv`; syntax checks belong to Spectral.
Wire anything you add into `.github/workflows/toolbox-ci.yml` in the same PR — a validator
nobody runs is documentation, not a gate.
