# R2-H-2 — circuit breaker: review annotations

Annotations attached to review finding **R2-H-2** and its follow-up ticket
"Governance Portal circuit breaker is mock-defaulted and still a symmetric toggle".
Recorded here rather than in a spec because they describe the ticket and the system,
not one feature's requirements.

## The follow-up ticket is scoped to the wrong scenario

The ticket is written as a Scenario A concern: it says R2-H-2 hardened the Scenario A
`AutomatedMarketMaker` and that "the Governance Portal frontend was not updated".

Finding 1 of that ticket — the mock-default data path — is **Scenario B behaviour**.
`VITE_USE_MOCKS` is consumed in `scenario-b/frontend/apps/governance/` by
`governance.api.ts` and `registry.api.ts`. Scenario A declares the same variable but no
Scenario A source file reads it, so its toggle is inert and switching it changes nothing.

Findings 2 to 4 (symmetric toggle, `tx_hash` not surfaced, status as source of truth) are
likewise addressed in Scenario B, where the breaker actually drives an AMM. The work was
therefore delivered under spec `043-breaker-txhash-mock-docs` against Scenario B, and the
Scenario A side is handled separately: its AMM is vestigial and its retirement is tracked
under spec `044-scenario-a-amm-retirement`.

Read the ticket's scenario labels as indicative only. The scenario isolation rule still
applies: the two are not to be changed together beyond the documentation corrections that
describe each one accurately.

## Breaker actions write no governance audit-trail entry

Discovered while verifying 043, pre-existing, and deliberately not fixed there.

Pause, resume-proposal and resume-signature each write a `CircuitBreakerSignature` row and
now carry an on-chain transaction hash, but **none of them appends to the governance audit
log** that the portal's "Recent Governance Events" table and the Audit screen read. An
operator reviewing the audit trail sees no record that swaps were halted or resumed.

Confirmed on a live two-central-bank stack on 2026-08-24: after a full pause →
resume-proposal → resume-signature cycle on `W-BRL-W-ARS`, the Brazil governance portal's
Recent Governance Events table still listed only `GOVERNANCE_BOOTSTRAP`.

This matters beyond convenience: the constitution requires the breaker lifecycle to be
observable, and account freeze/unfreeze — the other emergency control on the same screen —
does append audit entries. The asymmetry is not deliberate.

Fixing it means appending an audit entry alongside each signature row, with the actor, the
pair, the action and the transaction hash. It is out of scope for 043, which was limited to
making the on-chain reference visible; it needs its own card and its own tests.

## Resume reports LIVE as soon as the expected final signature lands

Recorded in full where a maintainer meets it, as a comment on `ExecuteResume` in
`scenario-b/backend/services/api-gateway/internal/services/circuit_breaker_service.go`.

In short: the AMM auto-unpauses inside `signResume` once quorum is met, so `ExecuteResume`
makes no chain call. The caller reports the resumed state as soon as the final *expected*
signature lands. That is correct for the 2-of-N quorum every current environment uses, but
would report LIVE prematurely for any quorum above 2. Raising the resume quorum requires
reworking that path to confirm on-chain state before reporting LIVE.

## A re-pause does not clear the previous resume proposal

Discovered while verifying 043 on a live stack, pre-existing, not fixed there.

`GetStatus` discovers an in-flight resume proposal from the AMM's own events
(`ActiveResumeProposal`). Pausing a pair again does not invalidate the proposal from the
previous cycle, so a freshly halted pair reports `RESUME_PENDING` with the old proposal id
and its already-satisfied signature count.

Observed on 2026-08-24: immediately after a pause, `W-BRL-W-ARS` reported
`state: RESUME_PENDING`, `resume_signatures: 2`, `resume_quorum: 2`. The portal rendered
"2/2 signatures" on a pair that had just been stopped, which reads as "about to resume".

The network-wide indicator is unaffected — it maps `RESUME_PENDING` to halted, so the
chrome banner stays correct — but the per-pair screen misleads the operator. The fix
belongs in the contract or in the proposal-discovery path, not in the portal, and needs
its own card.

## The status poll asks every pair on every tick

Recorded during the review of 043, not fixed there.

The chrome polls `fetchState` every 15 seconds
(`scenario-b/frontend/apps/governance/src/components/layout/AppLayout.tsx`), and
`fetchState` reads **every** active pair's status in parallel
(`stores/circuit-breaker.store.ts`) to derive the one network-wide claim the banner makes.
The cost is therefore `pairs x 4 requests/minute` per open portal, from any route, and it
grows with the corridor count rather than with what the operator is looking at.

Each of those requests is now cheap on the gateway side — the breaker lookups read only the
blocks that appeared since the last poll (`shared/blockchain/scenariob/amm/breaker_scan.go`)
— so this is a shape problem, not a performance one today. The fix is an aggregate endpoint
that answers "is any pair halted" in one call, which is a backend contract change plus a
store rewrite: its own card, with its own tests. Reducing the interval instead would trade
banner freshness for load without addressing the fan-out.
